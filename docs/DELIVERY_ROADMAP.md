# Delivery roadmap: prove a useful plant job

Working priorities, updated 2026-11-09 UTC. The original [PLAN.md](PLAN.md) remains the dated research/showcase plan.
This roadmap prioritizes useful delivery from the existing tools before more catalog breadth.

The [current self-service gap record](SELF_SERVICE_GAPS.md) now links reusable export intake, real agent sessions
and repeat-revision evidence. PR46/47 are merged with passing main CI. The declared
native CAD campaign is complete as a negative full-save/paper qualification;
bounded model/metadata receiving does not satisfy native preservation or readable
paper delivery. Keep those failures visible rather than widening that campaign.

The next software depth is [one unit's foundation handoff](FOUNDATION_HANDOFF.md):
selected history, drawing findings and notes, an actual supported receiver, full
typed readback, revised sources, conflicts and export/reopen. Follow the
[preimplementation plan](../examples/foundation-cycle/PLAN.md). The local receiver
does not complete the separate human/company receiving priorities below. Before
more breadth, measure one real engineer/manager result and one authorized
destination's acceptance/next revision when participants become available.

The primary readers are maintenance and engineering managers. The [manager starting guide](MANAGERS_START_HERE.md)
and [offline review packet](../examples/manager-review/README.md) put the decision, source preparation, named
owners, receiving verification and actual effort ahead of choosing a platform. Work planning, asset information,
drawing recovery and project/change handoff are the first jobs; broader methods remain available behind them.

The [repository guide](REPOSITORY_GUIDE.md) owns directory/reference organization;
the [workflow reproduction guide](REPRODUCE_A_WORKFLOW.md) supplies executable entry
commands and the source/interpretation/receiving boundaries. Its portable fixture
runner now checks seven current routes beside wrong-input and revision controls.
This implements the software-discovery/repetition part of the first-result trial.
Actual recipient effort, usefulness and company readback remain separate observations.

| Priority | Work | Observable completion |

| 1 | Make maintenance reconciliation and drawing recovery easy to start | Runnable examples, own-input steps, defined outputs and a direct contact path. |

## Use public resources first

Reuse the public OPEN100/DEXPI sources, the fictional maintenance replacement and attributed photo exercise.
Keep separate source families separate: a public motor photograph is not evidence about the fictional valve.
No model subscription is needed to inspect the saved examples. A better reader can be evaluated in the
[existing slot](PLUG_IN_A_READER.md); building another reader is not a prerequisite to a useful handoff.

For CAD comparisons use the actual target's public documentation and supported exchange profile. Preserve
third-party licenses; do not copy implementation code from an incompatible project. Existing platforms already
provide [diagram parsing and graph contextualization](https://docs.cognite.com/cdf/integration/guides/contextualization/diagram_parsing).
Evaluate buying, partnering or adapting against the scoped engineering job rather than claiming a new category.

The [2026-11-08 platform comparison](COMPETITIVE_WORKFLOWS.md) records Entellia/Flow2MTP's connected
engineering and brownfield positioning beside Cognite and Siemens offerings. Before adding formats or
another generation feature, identify the client's existing tools and the source preparation, interpretation
or receiving job still needing help. The optional requirements/handoff worksheet deepens that review;
it does not create an MTP integration or a new product category.

[ChemE-as-Code and Process Atlas](https://www.pi-research.org/post/26-11-05-cheme-as-code/) were publicly released
on 2026-11-05 with linked engineering files, external calculation tools and consistency/freshness checks. Its
authors report an agent-created preliminary engineering package and explicitly state that no independent
engineer reviewed that design. Treat it as relevant prior art and a possible source of separately qualified
public examples, not validated plant truth or evidence of an exclusive market gap. Do not copy third-party
code or data without checking their respective licenses. This delivery uses no code from that project.

## Depth gates

### Measure the whole first result

For component generation, include the [editable takeover and correction lessons](COMPETITIVE_WORKFLOWS.md#moshe-baum-keep-generated-components-useful-for-the-engineer-who-edits-them).
Start from the same selected map/context and required output under both methods.
Retain preparation, retries, review, manual correction, receiving and regeneration
effort separately. Demonstrate one useful human edit and verify it survives or is
explicitly reported on the next generation. A fast render, software-only timing
or an exported editable-looking file does not establish that an engineer can
continue the job efficiently. No new human timing result is supplied here.

The [Flowstead browser launch](COMPETITIVE_WORKFLOWS.md#flowstead-distinguish-the-calculation-from-the-unfinished-plant-job)
reinforces a useful delivery test: can someone reach, inspect and retain a result when the question arises?
The toolkit already has account-free committed examples and offline reports. That does not establish that
its Python preparation runs on a phone or that every report is usable at a phone width.

For the next self-service trial, select one existing job and freeze the records, question, expected finding,
scope and pass/fail checks before running. Keep these separate observations:

| Observation | Evidence to retain |
|---|---|
| Reach the first useful finding | Start at the actual shared repository link in a fresh environment. Record navigation, prerequisites, failed steps and elapsed preparation/execution time. The answer must identify one source-supported finding and its remaining unknowns. |
| Inspect the evidence | Follow the finding to both relevant source locations and the stated revision. Check readable content and usable controls at declared desktop and phone viewport sizes; retain failures. Desktop viewport emulation does not establish operation on a physical phone. |
| Keep working after the session | Save the report, editable inputs and source/mapping basis outside the active session. In a fresh environment, reopen and reproduce the selected finding using the documented route. A screenshot or browser cache alone does not pass. |
| Handle one returned revision | Use a predeclared changed source, retain the prior packet, rerun and identify what changed and what remains unresolved. An absent disagreement does not establish company acceptance. |
| Compare the complete job | Retain preparation, interpretation, review, rework and receiving effort against the same records, question and coverage under the existing method. No measured baseline means no measured saving. |

An author-run or agent-run exercise can test those software steps without employee testers. Label its actual
operator and exposure; it cannot supply a manager's usefulness judgment, engineering release or purchasing
decision. Record those separately when a real recipient is available. Keep a failed route in the results
rather than switching to a prepared example and calling the own-record path successful.

The [quote worksheet](../examples/consulting-start/QUOTE_WORKSHEET.md) and
[receiving record](../examples/consulting-start/REVIEW_AND_NEXT_JOB.md) capture which parts the client can
already do and which outside contribution it would pay for. This is the next delivery measurement, not a
reason to add accounts, a new solver or a general browser application ahead of a recurring job.

The existing backlog already contains the important unrun exercises: N052 (timed human drawing review), N062
(actual recipient usefulness) and N063 (company handoff and subsequent revision). Software receipts do not close
those items. Use [ACCEPTANCE.md](ACCEPTANCE.md) and retain failures as well as passes. Public sources remove the
need for private data in an initial recipient trial; they do not supply a human participant or a company's system.

Defer speculative connectors, more equipment classes, another general ontology, additional 3D showcases and
autonomous write workflows unless a concrete delivery job requires them. Fix current regressions and keep the
[status](STATUS.md), source limitations and [feature evidence](FEATURES.md) current.

The assistant interface is replaceable. Portable source-linked information should remain useful in CAD, a CMMS,
search or an approved copilot. Microsoft supports both indexed and federated external-content routes, each with
its own deployment and authentication requirements ([connector overview](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/overview-copilot-connector)).
An MCP protocol pass does not establish company Copilot acceptance.

## Alerts: detection and maintained delivery

An updated drawing, a replacement work order or a revised datasheet can leave an earlier answer unsupported.
The toolkit already supplies explicit [map comparisons](ONE_MAP.md) and
[context refresh/staleness checks](CONTEXT_REGISTER.md). Someone must run them on supplied versions; there is
no background source watcher or notification service. A revised source means **review the affected conclusion**,
not that the source's new value is approved or the installed asset has changed.

| Responsibility | Toolkit starting point | Maintained service or approved company system |
|---|---|---|
| Detect a relevant difference | Compare selected old/new sources, mapped identities, conflicts and dependent answers; retain evidence and unknowns. | Acquire authorized revisions on a schedule or event, track checkpoints and detect gaps in collection. |
| Decide whether a person needs to act | Supply the affected item, reason and proposed review need. | Resolve the current owner and permissions; separate action-needed items from FYI/digest activity. |
| Deliver and follow through | Export inspectable results through supported contracts. | Route notifications, deduplicate retries, record delivery failures, acknowledge, reassign and escalate under agreed rules. |
| Resolve the condition | Retain the old/new basis and later supplied review history. | Verify the accepted correction/readback; acknowledgment alone does not resolve a record disagreement. |

For example, a work order records a valve replacement while the datasheet still shows the old size. A useful
review item identifies the same position, both revisions, the disagreement, the record owner and the requested
check. Repeated polling of the same unresolved disagreement should not create another notification each time.
A new revision or a changed review basis must remain visible rather than being hidden by that deduplication.

Before implementing an integration, agree its minimum event record: stable subject ID, condition and event ID,
old/new source fingerprints and locators, detection time, collection checkpoint, review reason, responsible
owner and permissions, action-needed/FYI class, and resolution basis. This is a **proposed interface**, not a
currently emitted toolkit event schema or an implemented connector.

Test unchanged polling, duplicate delivery, missed/reordered revisions, an unavailable source, permission/owner
changes, failed delivery, acknowledgment without correction, resolution and recurrence. A failed collection or
check is unknown/unavailable, not an all-clear. Notification content and links must respect the recipient's
current access. Keep sustained failures observable even when repeat notifications are grouped or suppressed.

Start with one real stale-source or record-conflict job and measure relevance, false positives, missed changes,
delivery and useful resolution. A customer-approved scheduled job and existing task system can support an early
consulting engagement; using the toolkit must not depend on a future product launch. A managed service can add
ongoing ownership. Process alarms, trips and protection systems remain separate from these information-review
alerts; this roadmap does not propose replacing them.
